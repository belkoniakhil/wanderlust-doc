# WANDERLUST 2.0
## Master Project Blueprint & Technical Execution Document

**Project Type:** Scalable Rental Booking Platform  
**Project Architecture:** Horizontally Scalable Modular Monolith  
**Primary Goal:** Build an original rental booking platform and evolve it into a distributed, containerized, load-balanced application with Redis caching.

**Budget:** ₹0 — Free-tier services and open-source technologies only  
**Development Approach:** Incremental implementation, one feature at a time  
**Primary Objective:** Strong portfolio project, practical system design knowledge, and interview-ready engineering experience.

---

# 1. PROJECT VISION

Wanderlust 2.0 is an original accommodation and rental booking platform inspired by applications such as Airbnb.

However, this project is not simply about creating another rental booking website.

Our primary objective is to understand how a backend application can evolve from a simple Node.js application into a horizontally scalable system.

We will first develop a fully functional rental booking application.

Once the application is stable, we will introduce infrastructure and system design concepts incrementally:

1. Docker containerization.
2. Multiple backend instances.
3. Nginx reverse proxy and load balancing.
4. Redis caching.
5. Cache invalidation and expiration.
6. Shared session management.
7. Performance testing and benchmarking.

We will not implement all these technologies simultaneously.

Every feature must be implemented, understood, tested, and documented before moving to the next stage.

## Core philosophy

- Build our own application from scratch.
- Understand every important line of code.
- Avoid blindly copying tutorial implementations.
- Prefer a modular monolith over premature microservices.
- Introduce technologies only when there is a practical reason.
- Keep the project deployable throughout development.
- Avoid unnecessary paid services.
- Measure performance instead of making unsupported performance claims.

# 4. APPLICATION FUNCTIONAL REQUIREMENTS

Before introducing distributed infrastructure, we need a working application.

The platform will have the following features.

## 4.1 User authentication

Users should be able to:

- Register.
- Log in.
- Log out.
- Maintain authenticated sessions.
- Access protected routes.
- Update their profile.

Authentication will initially use Passport.js with a local username/password strategy.

Passwords must be hashed securely.

We will initially use Express Session. Later, its session store will be migrated to Redis to support multiple backend instances.

## 4.2 Property listing management

Authenticated users should be able to:

- Create property listings.
- View all listings.
- View individual property details.
- Edit their own listings.
- Delete their own listings.
- Upload property images.

Each listing should contain fields such as:

- Title.
- Description.
- Location.
- Country.
- Price per night.
- Property images.
- Category.
- Owner.
- Creation timestamp.

Only the listing owner should be allowed to modify or delete their property.

## 4.3 Search and filtering

Users should be able to:

- Search by location.
- Filter properties by price.
- Browse available listings.
- Navigate between pages using pagination.
- View listing details.

Search results will become one of our primary Redis caching candidates.

## 4.4 Reviews and ratings

Users should be able to:

- Add reviews.
- Rate properties.
- View existing reviews.
- Delete or modify their own reviews.

We will implement authorization checks to prevent users from manipulating reviews belonging to others.

## 4.5 Booking functionality

Users should be able to:

- Select check-in and check-out dates.
- Create a booking.
- View their bookings.
- Cancel bookings according to our defined rules.

The backend must validate date ranges and prevent overlapping bookings for the same property.

We will implement appropriate database-level consistency controls when booking functionality is developed.

Payment integration is outside the initial project scope.

# 6. DATABASE ARCHITECTURE

## Decision: One shared MongoDB database

We will use one MongoDB database shared by all backend instances.

We will NOT create separate databases for Node.js instance 1, instance 2 and instance 3.

Why?

Imagine:

1. A user creates a listing through Node instance 1.
2. Another user accesses Node instance 2.
3. The second instance must retrieve the same listing.

If every instance has a separate database, data synchronization becomes unnecessarily complicated.

Our architecture must have a single source of truth.

### Database collections

Initially, we expect the following collections:

- users
- listings
- reviews
- bookings

We will add appropriate references, validation and indexes.

### Database indexing

We will introduce indexes for frequently queried fields, such as:

- Listing location.
- Listing owner.
- Booking property.
- Booking date fields.
- User email.

Indexes will be based on actual query patterns rather than created randomly.

### Database hosting

Our initial preference is MongoDB Atlas free tier, subject to current free-tier limits.

We may also run MongoDB locally through Docker if required.

The choice will be finalized during infrastructure setup.

All backend instances must use the same database connection configuration.

# 7. DOCKER ARCHITECTURE

## Why are we using Docker?

Docker packages our application and its runtime dependencies into a reusable image.

We can then create multiple containers from the same image.

Instead of manually installing and configuring the application for every instance, we build the image once and run it multiple times.

### Important distinction

- Docker image: Reusable application blueprint.
- Docker container: Running instance of an image.
- Docker Compose: Tool for defining and managing multiple containers.
- Physical/cloud machine: Infrastructure on which containers execute.

Docker does not automatically provide load balancing.

Nginx will perform that responsibility.

## Our target container arrangement

Initially, our local development environment will contain:

1. Nginx container.
2. Node.js application container 1.
3. Node.js application container 2.
4. Node.js application container 3.
5. Redis container.

MongoDB may initially be hosted through MongoDB Atlas rather than locally.

If we choose local MongoDB later, it can also be added to Docker Compose.

### Docker image strategy

We will:

- Create one Dockerfile.
- Build one Wanderlust application image.
- Reuse that image for all three backend containers.
- Supply different environment variables or instance identifiers when required.
- Keep application code identical across instances.

### Docker Compose responsibilities

Docker Compose will manage:

- Application containers.
- Nginx container.
- Redis container.
- Internal networking.
- Environment variables.
- Container dependencies.
- Health checks.
- Persistent storage where necessary.

We should use container DNS/service names for internal communication rather than hardcoding container IP addresses.

# 8. HORIZONTAL SCALING

## What are we implementing?

We will run three copies of the same Node.js backend.

For example:

- Node instance 1.
- Node instance 2.
- Node instance 3.

Each instance will execute the same application code.

Initially, we will run them on one physical laptop using Docker.

This demonstrates application-level horizontal scaling.

It is important to document that three containers on one laptop are not three independent physical servers.

### Why three instances?

To understand:

- Horizontal scaling.
- Request distribution.
- Shared state.
- Stateless application design.
- Instance failure.
- Resource utilization.
- Performance differences.

### Stateless architecture requirement

All backend instances must behave consistently.

We must avoid relying on local process memory for shared application state.

For example:

- Authentication sessions must be shared.
- Cache data must be shared.
- Important application data must be persisted in MongoDB.
- Temporary local files must not be required by another instance.

This is one of our most important architectural decisions.

# 9. NGINX LOAD BALANCING

Nginx will act as our reverse proxy and load balancer.

Users should not communicate directly with individual backend instances.

Instead:

User → Nginx → Backend instance

### Target architecture

                  USERS
                    |
                    v
             NGINX LOAD BALANCER
                    |
          +---------+---------+
          |         |         |
          v         v         v
       NODE 1    NODE 2    NODE 3
          |         |         |
          +---------+---------+
                    |
          +---------+---------+
          |                   |
          v                   v
        REDIS              MONGODB

### Load-balancing strategy

We will initially implement round-robin load balancing.

Example:

- Request 1 → Node 1.
- Request 2 → Node 2.
- Request 3 → Node 3.
- Request 4 → Node 1.

We will use Nginx upstream configuration.

### Nginx responsibilities

- Receive incoming HTTP requests.
- Forward requests to backend instances.
- Distribute traffic.
- Forward relevant headers.
- Support health-related routing behavior where configured.
- Handle proxy timeouts.
- Provide a single application entry point.

### Important testing

We will create an endpoint such as:

GET /health

The response will include:

- Application status.
- Instance identifier.

For example:

{
  "status": "healthy",
  "instance": "node-2"
}

This allows us to verify which instance handled each request.

We will also simulate stopping one container and observe how Nginx behaves.

We must distinguish between simple upstream failover and full active health checking. We will not claim capabilities that our chosen Nginx configuration does not actually provide.

# 10. REDIS CACHING

## Decision: One shared Redis instance

All three backend instances will use the same Redis instance.

We will not create a separate Redis instance for each Node.js container.

Why?

Suppose Node 1 fetches a popular property and stores it in its local cache.

If Node 2 receives the next request, it will not know about Node 1's local cache.

This would defeat our shared caching objective.

Instead, Redis will provide a common cache.

### Redis responsibilities

Initially:

1. Cache popular property listings.
2. Cache individual property details.
3. Cache search results where appropriate.
4. Store shared authentication sessions.
5. Provide a shared infrastructure for future background jobs if added.

### Cache-aside pattern

We will implement the Cache-Aside Pattern.

Example:

User requests a listing.

Step 1: Check Redis.

Step 2: If the data exists, return it.

This is called a CACHE HIT.

Step 3: If the data does not exist, retrieve it from MongoDB.

This is called a CACHE MISS.

Step 4: Store the MongoDB result in Redis.

Step 5: Return the response.

Flow:

       CLIENT REQUEST
              |
              v
         REDIS CHECK
              |
        +-----+-----+
        |           |
      HIT          MISS
        |           |
        v           v
     RETURN      MONGODB
     DATA           |
                    v
                 REDIS
                    |
                    v
                RETURN DATA

### Cache invalidation

This is extremely important.

Imagine a property owner updates a listing.

The previous property data may still exist in Redis.

If we do nothing, users may receive outdated data.

Therefore:

- Create listing: Ensure relevant cached search results cannot hide the new listing.
- Update listing: Invalidate the listing details and relevant search caches.
- Delete listing: Invalidate the listing and relevant search caches.
- Review update: Invalidate cached listing data if ratings or review counts are included.

We will implement cache invalidation through the relevant service layer.

### TTL

TTL means Time To Live.

Every cached value should have an expiration policy.

For example, we may initially choose:

- Listing details: 5 minutes.
- Search results: 2 minutes.
- Popular listings: 10 minutes.

These are initial experimental values, not permanent requirements.

We will tune them based on testing.

### Redis performance measurement

We will measure:

- Cache hits.
- Cache misses.
- Cache hit ratio.
- Response latency.
- MongoDB query reduction.

We must not claim that caching improves performance by a specific percentage until we measure it.

# 11. DISTRIBUTED SESSION MANAGEMENT

This is a necessary part of supporting multiple backend instances.

Initially, Passport.js and Express Session will manage authentication.

However, using the default in-memory session store is unsuitable for our multi-instance architecture.

Example problem:

1. User logs in through Node 1.
2. Session exists only in Node 1's process memory.
3. Next request reaches Node 2.
4. Node 2 cannot find the session.

This causes authentication problems.

### Our solution

Use a Redis-backed Express Session store.

All three backend instances will use the same Redis session store.

Expected flow:

User Login
    |
    v
Node Instance 1
    |
    v
Redis Session Store

Later request:

User
    |
    v
Node Instance 2
    |
    v
Redis Session Store
    |
    v
Authenticated User

We will configure:

- Shared session store.
- Consistent session secret.
- Secure cookie settings appropriate for the deployment environment.
- Session expiration.
- Session regeneration on login.
- Proper logout behavior.

This is separate from listing caching, even though both use Redis.

# 15. IMPORTANT ARCHITECTURAL RULES

These decisions must be preserved throughout development.

### Rule 1: One application codebase

All three backend instances must use the same source code and Docker image.

### Rule 2: One shared MongoDB database

All instances access the same persistent data source.

### Rule 3: One shared Redis instance

All instances use the same Redis cache and session store.

### Rule 4: Nginx is the entry point

In our local distributed setup, clients access the application through Nginx rather than connecting directly to individual application containers.

### Rule 5: Backend must be stateless

No important shared state should depend on one particular Node.js process.

### Rule 6: Environment-based configuration

Do not hardcode database credentials, Redis URLs, secrets or deployment-specific values.

### Rule 7: Incremental implementation

Do not implement multiple new infrastructure features simultaneously.

### Rule 8: Preserve existing working functionality

Before introducing a new infrastructure component, establish a working baseline and keep a known-good Git version.

### Rule 9: Test every change

Every feature must be tested before moving forward.

### Rule 10: No fake scalability claims

Three Docker containers on one laptop are not three independent physical servers.

Performance improvement must be demonstrated with measurements.
